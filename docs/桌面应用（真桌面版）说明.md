# AI 数字人 · 真桌面应用说明（AILiveDesktop）

> 这一版不再是"浏览器里做成像桌面的界面"，而是**一个真正的 Windows 桌面程序**：
> 独立 `AILiveDesktop.exe`、独立进程、原生窗口与任务栏图标、自己托管后端服务、带安装包与卸载。
> 界面形态也从"图标 + 任务栏的仿桌面"换成了**常规桌面软件界面**：左侧导航栏 + 顶部工具栏 + 内容区 / 多标签页 + 底部状态栏。
>

> （`live_console.html`），而 `/desktop.html` 还会提供那套"网页里的假桌面"。现在服务端统一收口

## 一、先明确一件事：什么叫"真桌面应用"

桌面应用**内部用 WebView2（Chromium 内核）渲染界面**，这是业界通行做法（VS Code、Teams、飞书、微信小程序桌面版、大量 Electron/Tauri 应用都是这条路）。
所以本项目的"真桌面版"指的是下面这些**可验证的硬指标**，而不是"用 Win32/Qt 重画一遍界面"：

| 硬指标 | 本项目的实现 | 怎么自证 |
| --- | --- | --- |
| 独立可执行程序 | `AILiveDesktop.exe`（PyInstaller 打包，带图标与版本资源） | 右键属性 → 详细信息：产品名「AI 数字人桌面版」、版本 1.4.0 |
| 独立进程 + 原生窗口 | 进程名 `AILiveDesktop`，Win32 顶层窗口标题「AI 数字人桌面版」 | 任务管理器；`_e2e_desktop_app.py` 用 Win32 API 枚举窗口标题 |
| 后端由应用自己托管 | 启动时检测 8010：没有就自己拉起 LiveTalking，退出时停掉自己拉起的那一个 | 宿主日志 `[服务]` / `[退出]` 行；场景 managed 验收 |
| 安装包 | 桌面 + 开始菜单快捷方式、HKCU 卸载项（控制面板可卸载） | `_e2e_installer.py` 22 项 |
| 单实例、可持久化 | 端口 8011 单实例锁；WebView2 用户目录持久化登录态与设置 | `%LOCALAPPDATA%\AILiveDesktop\webview` |
| 崩溃不留僵尸 | 退出看门狗：界面请求退出后主循环若未结束，兜底结束进程并（必要时）停服务 | 宿主日志 `[退出]` 行 |

## 五、它怎么管理后端服务（托管决策）

| 启动时 8010 的状态 | 应用的做法 | 退出时 |

## 六点五、桌面端的界面从哪来（v1.3.0 起）

用户要的是"桌面端不要出现网页端的界面"，这一版按**本地界面源**做：

```
AILiveDesktop.exe
   ├── app\ui\            ← 随应用打包的界面副本（界面本体 + 各模块页 + 登录页 + 资源 + sha256 清单）
   │      desktop.html    ← 桌面端入口（就是 web\app.html 的固化副本）
   │      web\…           ← 其余界面文件（login.html / live_console.html / 各模块页 …）
   └── app\ui_server.py   ← 在 127.0.0.1 的独立端口（8015~8020，被占则换）同时提供两件事：
          GET /desktop.html、/、/app.html、/app、/index.html  → 自带的 desktop.html
          GET /web 之外的其它路径（/api/*、/offer、/whep、/record/*、WebSocket …）→ 反向代理给 8010
```

为什么不是"直接从磁盘加载 HTML"或"改界面代码去请求 8010"：
* 界面里有 `fetch(path, {credentials:'same-origin'})`、相对路径、iframe、`EventSource`、WebRTC——
  换源会立刻打断登录态与这些用法；**同源 + 反向代理**则一行界面代码都不用改。
* Cookie 是按**主机**作用域的（`127.0.0.1`，与端口无关），所以登录态在两个端口之间天然共享。

| 关心的问题 | 结论 |
| --- | --- |
| 桌面窗口会不会渲染 8010 的网页端页面 | 不会。`/`、`/app.html`、`/desktop.html` 全部映射到自带副本；验收里断言 `location.origin != 8010` |
| 界面靠什么保证和网页端一致 | 每次打包前 `vendor_ui.py` 自动重新固化并写 sha256 清单；`--check` 可查漂移 |
| 万一界面副本缺失 | 宿主会**大声记日志**并退回加载 8010 的页面（不会静默变白屏） |
| 登录怎么办 | 宿主开机先问一次 `/api/auth/me`：未登录就先把窗口送到**本地的登录页**（与网页端一致），登录成功后回到自带界面 |
| "用浏览器打开工作台" | `open_external` 会把本地界面源的地址换回 `http://127.0.0.1:8010/...`（本地端口随应用退出即失效，不能给外部浏览器） |
| 同一端口被别的进程占用 | `ui_server` 关掉了 `SO_REUSEADDR`——Windows 下它允许"绑定已被人监听的端口"，会造成两个进程共用一个端口、请求跑到别人家（实测踩到） |

## 六点六、桌面端 ↔ 网页端：哪些入口只属于桌面端（v1.3.1）

同一个界面文件（`LiveTalking\web\app.html`；桌面端渲染它的固化副本）在两端共用，但**桌面专属能力
在网页端不渲染**。判定函数是 `app.html` 里的 `isDesktop()`：

```js
function isDesktop(){ return params.get('host') === '1' || hasBridge(); }
```

* `?host=1`：宿主加载自带界面时一定带（`app\app.py` 的 `ui_entry_url()`），**不依赖 pywebview 注入时序**，
  窗口刚打开就能判对；
* `window.pywebview.api`：pywebview 注入的桌面桥接；
* 两者都为假 = 网页端（浏览器直接开 `http://127.0.0.1:8010/app.html`）。

| 入口 / 能力 | 桌面端（AILiveDesktop） | 网页端（浏览器 8010） | 为什么 |
| --- | --- | --- | --- |
| 默认入口（v1.3.2 统一） | 自带副本：本地界面源把 `/`、`/app.html`、`/desktop.html` 全部映射到 `desktop.html`（即统一外壳） | `GET / → 302 /app.html`、`GET /desktop.html → 302 /app.html`；`live_console.html` 等仍可直接访问 | 两端都只有一套界面；老书签也不会落到旧假桌面页 |
| 界面来源 | 随应用打包的副本，由本地界面源（8015~8020）同源提供 | 8010 服务直接提供 | v1.3.0 的"桌面端不出现网页端页面" |
| `文件 → 退出应用`（Ctrl+Q） | 有 | **无** | 退出应用 = 关进程 + 停掉自己启动的服务；浏览器里没有这个动作（网页端按 Ctrl+Q 不拦截） |
| `服务 → 重启数字人服务 / 打开日志文件夹` | 有 | **无** | 需要宿主重启子进程、调用系统打开本机文件夹 |
| 账号菜单 `打开项目文件夹` | 有 | **无** | 浏览器打不开本机文件夹 |
| 账号菜单 / 服务菜单里的"打开工作台" | `用浏览器打开工作台`（交系统浏览器） | `在新标签页打开工作台` | 在浏览器里"用浏览器打开"没有意义 |
| 设置 → 服务 | 服务地址/端口/运行模式 + **服务托管、界面内核** + 重启/日志文件夹/项目文件夹按钮 | 只有 服务地址/端口/运行模式 + `重新读取状态` | 网页端不托管服务、也管不到本机进程 |
| 关于面板 | 运行端信息含 **服务托管 / 界面内核 / 项目根目录 / 日志目录 / Python / 构建类型** + `打开项目文件夹` 按钮 | 改为 `运行端：网页端（浏览器）` + 浏览器 UA，**没有本机路径** | 网页端拿不到宿主信息，不该假装知道 |
| 标题 / 品牌小字 | `AI 数字人桌面版` / `桌面版 v1.3.1 · 已托管服务` | `AI 数字人 · 网页端` / `网页端` | 按端命名，网页端不再自称"桌面版" |
| `视图 → 全屏显示` | 宿主自实现全屏（第九节：铺满显示器 + 让任务栏让位） | 浏览器 Fullscreen API | 各用各自的能力，网页端不会去动任务栏 |
| 13 个模块 / 左导航 / 多标签 / 状态栏 / 主题 / 账号与套餐 / 权限判定 | 全部相同 | 全部相同 | 权限仍由服务端 `auth_middleware` 判定，外壳不替服务端放行 |

复跑（两条都是对**同一份界面**的两端断言，互为反向）：

```powershell
# 网页端：桌面专属入口必须"不存在"（17 项端区分断言）
E:\AiLive\env\python.exe E:\AiLive\tools\smoke\_e2e_app_ui.py

# 桌面端：桌面专属入口必须"存在"（4 项反向断言）
E:\AiLive\env\python.exe E:\AiLive\tools\smoke\_e2e_desktop_app.py --scenario external --app "$env:LOCALAPPDATA\Programs\AILiveDesktop\AILiveDesktop.exe"
```

改界面仍然只改 `LiveTalking\web\app.html`：桌面端副本由 `app\vendor_ui.py` 固化（打包脚本每次自动重跑），
`vendor_ui.py --check` 可查"副本与网页端是否漂移"。

## 七、打包（`app\build_exe.ps1`）

```powershell
powershell -ExecutionPolicy Bypass -File E:\AiLive\app\build_exe.ps1            # 正式版（无控制台）
powershell -ExecutionPolicy Bypass -File E:\AiLive\app\build_exe.ps1 -Console  # 调试版（带控制台，能看报错）
powershell -ExecutionPolicy Bypass -File E:\AiLive\app\build_exe.ps1 -Smoke    # 打完顺手自检启动一次
```

实测：约 33 秒完成，产物 `app\dist\AILiveDesktop\`（exe 5.28 MB / 整目录 40.2 MB），
`dist\BUILD-INFO.txt` 记录版本、时间、模式、大小与"自带界面 N 个文件 / N MB"。

打包脚本在 PyInstaller 之前会**先自动固化界面副本**（`env\python.exe app\vendor_ui.py`），
再 `--add-data app\ui;ui` 打进包里；副本不完整（缺 `desktop.html` / `MANIFEST.json`）会直接失败退出，
不会产出"界面其实是网页端"的包。

**本机踩过的坑（改打包脚本前务必知道）**：项目用的是 **conda 环境**，`_ssl`、`_ctypes` 等扩展模块依赖
`env\Library\bin` 下的 `libssl-3-x64.dll` / `libcrypto-3-x64.dll` / `libffi` 等 DLL，而 PyInstaller 只在 `PATH` 里找依赖。
脚本因此做了两件事：把 `env\Library\bin`、`env\DLLs`、`env` 前置进 `PATH`（让依赖被自动收集），并把 OpenSSL DLL 显式 `--add-binary`。
**症状对照**：运行时报 `ImportError: DLL load failed while importing _ssl / _ctypes` 就是这个原因。

## 八、安装 / 卸载

```powershell
# 安装（默认源 E:\AiLive\app\dist\AILiveDesktop）
powershell -ExecutionPolicy Bypass -File E:\AiLive\app\installer\install.ps1
# 指定项目目录（默认从安装源自动向上识别；-SkipProjectRoot 则跳过）
powershell -ExecutionPolicy Bypass -File E:\AiLive\app\installer\install.ps1 -ProjectRoot E:\AiLive
# 卸载：安装目录里的那份也能单独跑（源目录删了照样能卸）
powershell -ExecutionPolicy Bypass -File "$env:LOCALAPPDATA\Programs\AILiveDesktop\uninstall.ps1"
# 卸载但保留登录态与设置
powershell -ExecutionPolicy Bypass -File "$env:LOCALAPPDATA\Programs\AILiveDesktop\uninstall.ps1" -KeepData
```

**安装时会顺手"记住项目目录"**：安装目录在 `%LOCALAPPDATA%` 下，从那里向上是找不到数字人项目的，
所以安装器会从安装源逐级向上识别项目根（判定标准与宿主一致：同时有 `LiveTalking\app.py` 与 `env\python.exe`），
写进 `%LOCALAPPDATA%\AILiveDesktop\config.json` 的 `project_root`（只改这一个键，不动你已有的窗口尺寸等设置）。
这样**全新机器上装完，首次启动就不用再手动选目录**。卸载默认会删掉用户数据目录，所以"卸载→重装"会自动重新写入。

## 九、全屏：为什么自己做、怎么做的

用户报的现象：「界面 UI 全屏的时候没有完全覆盖」。查下来不是矩形算错，而是**任务栏压在上面**：

```
实测（本机 2560x1600 @150%，任务栏自动隐藏）
  Shell_TrayWnd hwnd=196646  exstyle=0x00000088  WS_EX_TOPMOST=True
  rcWork == rcMonitor（没有为任务栏预留工作区，说明任务栏是自动隐藏）
```

任务栏是**置顶窗口**，永远压在所有非置顶窗口之上；鼠标一碰屏幕底边，自动隐藏的任务栏就滑出来盖在
无边框全屏窗口上。pywebview 自带的 `toggle_fullscreen()` 只做"去边框 + 最大化 + 照显示器矩形"，
**不置顶**，所以必然被盖；而且实测"只置顶也不够"——外壳在弹出任务栏时会再把它抬到所有置顶窗口之上
（验收里用 `WindowFromPoint` 在屏幕底部命中到的仍是 `Shell_TrayWnd`）。

现在的实现（`app\desktop_window.py` 的 `FullscreenController`）：

| 环节 | 做法 | 为什么 |
| --- | --- | --- |
| 边框 | WinForms `FormBorderStyle=None`（让 WinForms 自己的状态一致，避免它稍后把边框改回来） | 只改 Win32 样式会被 WinForms 覆盖回去 |
| 几何 | `GetMonitorInfoW` 取当前显示器的**物理像素**矩形 → `SetWindowPos(...SWP_FRAMECHANGED)` | 多显示器 / 高 DPI 都准；实测窗口矩形 == 显示器矩形 |
| 置顶 | 全屏期间 `HWND_TOPMOST`；**只在窗口是前台时**保持，一旦切到别的程序立刻降回普通层 | 挡住任务栏，但不挡别的程序 |
| 任务栏 | 全屏期间 `ShowWindow(Shell_TrayWnd, SW_HIDE)`（含各显示器次级任务栏）＋ `ITaskbarList2::MarkFullscreenWindow`；看门狗每 0.4s 复查并自愈 | 这是"完全覆盖"的确定性保证；失焦或退出立刻 `SW_SHOWNA` 还原 |
| 崩溃兜底 | 隐藏任务栏期间写 `%LOCALAPPDATA%\AILiveDesktop\fullscreen_tray.json`，下次启动若发现标记还在就先把任务栏还原 | 被强杀也不会留下"任务栏不见了"的状态 |
| 退出 | 还原窗口样式 + `SetWindowPlacement`（含原来的最大化状态）+ 取消置顶 + 还回任务栏 | 实测：退出后窗口矩形与进入前**完全一致**，任务栏功能正常 |

退出方式：菜单「视图 → 全屏显示」再点一次，或按 **Esc**（宿主注入）。

真机验收（`tools\smoke\_e2e_desktop_fullscreen.py`，源码与打包 exe 各一轮 **19/19**）：

* 全屏后窗口矩形 `[0,0,2560,1600]` == 显示器矩形；页面视口 `1707x1067` == 屏幕 CSS 尺寸（dpr 1.5）；
* 全屏后 `topmost=True`、可见任务栏数 0；
* **把鼠标推到屏幕底边再取该点最上层窗口，命中的是应用窗口本身**（修复前命中 `Shell_TrayWnd`）——这条就是用户报的现象；
* 退出后窗口矩形与进入前一致、不再置顶、任务栏已还原，且**鼠标触底仍能弹出任务栏**（没把系统弄坏）。

## 十二、改代码前必读（三条血泪约束）

1. **`HostApi` 的实例属性必须以下划线开头**（`self._window` / `self._boot` / `self._log` …）。
   pywebview 是用 `dir(obj)` 扫描 js_api 方法的：它会**递归进任何"非可调用且带 `__module__` 的属性"**。
   一旦挂上 `Window`/`Boot` 这种对象，就会钻进 .NET 原生对象图，报
   `maximum recursion depth exceeded` 与 `CoreWebView2Controller members can only be accessed from the UI thread`，
   结果是 **js_api 方法列表为空**、进程还会卡几分钟。这是本项目最贵的一个坑。
2. **程序里销毁窗口前必须先把 `window.confirm_close` 置为 `False`**。pywebview 的 `on_closing` 在 `confirm_close=True`
   时会弹一个原生 MessageBox 等用户点确定，主循环就一直不返回（实测被卡住，只能等看门狗强杀）。
   界面自己已经确认过了，所以 `close_window()` 里先关掉它，再 `destroy()`，并挂 12 秒兜底看门狗。
3. **给 pywebview 的启动页 URL 要传"纯路径"，不要 `file://`**。pywebview 的 `is_local_url()` 实现是反的：
   只有"没有 scheme 的普通路径"才被当成本地文件并启用内置 http 服务；传 `file://` 会让页面留在 `file://`，
   js_api 一个方法都不会注入（症状：启动页永远不跳转）。

另外：`splash.html` 必须每轮轮询都重新读一次 `window.pywebview.api`（首屏注入存在竞态），
`.ps1` 带中文要 UTF-8 BOM + CRLF，`.cmd` 要纯 ASCII + CRLF（原因见 `tools\smoke\_check_script_encoding.py` 注释）。
